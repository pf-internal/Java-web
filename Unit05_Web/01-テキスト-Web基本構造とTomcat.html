復習1：なぜDAOとして分離すべきか（保守性）

カバ先生：「Unit04 まででDAO の書き方は身についてきましたね。ここで一度、なぜDAOとして分離するのかを整理しておきましょう。」

問い：なぜデータベースへの接続処理をDAOとして分離すべきなのか、保守性の観点から説明してください。

結論（覚える一文）

DAOは「DBとのやり取り（変更が起きやすい部分）」を1か所にまとめ、変更・バグ修正・テストの影響範囲を最小化するために分離する。

保守性のポイント（写経して覚える）

  • 変更点を1か所に集約できる（DB接続URL・ユーザー・パスワード、JDBCドライバ、SQLの修正）
  • 「データの取り出し方」と「使い方」を分離できる（DAO：SQL/JDBCの詳細 ／ それ以外：何をしたいか）
  • テストがしやすくなる（DAOだけ差し替えて、DBなしでも上流の動作確認がしやすい）
NG例（この形を避ける）
画面やServletの中に、SQLやJDBCの細かい手順が散らばっている
→ 仕様変更のたびに複数箇所修正になり、壊れやすい

復習2：DTOとEntityの違い

結論（覚える一文）：Entityは「DBの行」を表し、DTOは「画面や処理が使いやすい形に運ぶ箱」。

[DB]                         [アプリ]
テーブル1行                 画面/処理で使うデータの形

┌──────────────────┐        ┌──────────────────────┐
│ sales_table        │        │ SalesSummaryDto       │
│ id (PK)            │        │ totalAmount           │
│ sale_date          │  →DTO→ │ displayDate           │
│ amount             │        │ shopName              │
│ shop_id (FK)       │        │ ...（必要な形に編集） │
└──────────────────┘        └──────────────────────┘
        ↑
      Entity
  SalesEntity（列とほぼ1対1）
  • Entity：テーブルの列とほぼ1対1。DB設計変更の影響を受けやすい（DB寄りの層で管理）
  • DTO：画面・処理・APIの都合で必要な項目だけ集める／名前や型を整える。複数Entityの情報が混ざってもよい

ナナコ：「つまり Entity は DB の形そのまま、DTO は『使いやすいように詰め替えた宅配ボックス』みたいなイメージですね。」

カバ先生：「いいたとえです。今日は、そのDAOが作ったデータをブラウザ画面まで届ける経路 ― Webの仕組みとTomcat ― を学びます。」

チャプター3：クイズ

カバ先生：「解答は折りたたみの中にあります。まず自分で考えてから開いてください。」

【第1問】 GETメソッドについて、最も適切な説明はどれ？

  • A. リクエストボディ（Body）に主要データを載せて送るのが基本である
  • B. URLにパラメータが付くことが多く、同じURLなら再実行しやすい
  • C. 必ずデータ更新に使うメソッドである
解答例

正解：B

GETはURLに情報が乗りやすく、表示・検索などの「取得」によく使う。同じURLを再実行しても副作用が起きにくいのが特徴。

【第2問】 POSTメソッドがふさわしいケースはどれ？

  • A. 商品一覧を表示するだけの画面を開く
  • B. フォームの入力内容を送信して、登録処理を行う
  • C. 画像やCSSなどの静的ファイルを取得する
解答例

正解：B

POSTは送信するデータ（Body）を持ちやすく、登録・更新の処理で使う。URLに値が露出しないため、パスワードや個人情報の送信にも適している。

ユウタ：「GET は『見るだけ』、POST は『送る・変える』って覚えたらいいですね！」

写経ポイント①：フォルダを「箱」として覚える

カバ先生：「次のフォルダ構造をノートに書き写してください。どの箱が外から見えて、どの箱が見えないかがポイントです。」

Tomcat
 └ webapps
    └ アプリ名（コンテキスト）
       ├ （公開される領域）HTML / CSS / 画像など
       └ WEB-INF（外から直接見えない）
          ├ classes（Javaのクラス）
          └ lib（ライブラリjar）

写経ポイント②：リクエストの流れを2行で 

URL →（Tomcat）→ アプリに振り分け
リクエスト →（アプリ）→ 処理 → レスポンス
コピー用（ドラッグで貼り付け）

チェックポイント（これだけ描ければOK）

Webの循環（矢印が必須）

  • ブラウザ →（HTTPリクエスト）→ Tomcat
  • ブラウザ ←（HTTPレスポンス）← Tomcat

Tomcatの箱の中

  • webapps → アプリ名 → WEB-INF → classes / lib

言葉で言えること（短く）

  • 「ブラウザはHTTPで依頼する」
  • 「Tomcatがアプリに渡して処理する」
  • 「処理結果がHTTPレスポンスで戻る」
