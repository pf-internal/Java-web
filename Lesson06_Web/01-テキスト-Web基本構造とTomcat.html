前回の復習

復習1：なぜDAOとして分離すべきか（保守性）

カバ先生：「DBとのやり取り（変更が起きやすい部分）」を1か所にまとめ、変更・バグ修正・テストの影響範囲を最小化するために DAO として分離します。

保守性のポイント

  • 変更点を1か所に集約できる（DB接続URL・ユーザー・パスワード、JDBCドライバ、SQLの修正）
  • 「データの取り出し方」と「使い方」を分離できる（DAO：SQL/JDBCの詳細 ／ それ以外：何をしたいか）
  • テストがしやすくなる（DAOだけ差し替えて、DBなしでも上流の動作確認がしやすい）
NG例：画面や Servlet の中に SQL や JDBC の細かい手順が散らばっている
→ 仕様変更のたびに複数箇所修正になり、壊れやすい

復習2：DTOとEntityの違い

カバ先生：Entity は「DBの行」をそのまま表すクラス。DTO は「画面や処理が使いやすい形に運ぶ箱」です。複数テーブルの情報を混ぜてもよく、名前や型を整えて渡します。

  • Entity：テーブルの列とほぼ1対1。DB設計変更の影響を受けやすい
  • DTO：画面・処理の都合で必要な項目だけ集める／名前や型を整える。複数Entityの情報が混ざってもよい

HTTP の全体像（要点）

カバ先生：ブラウザとサーバのやり取りは「リクエスト（依頼）とレスポンス（返答）」の繰り返しです。リクエストには4つの要素があります。

ブラウザ →（HTTPリクエスト）→ サーバ
ブラウザ ←（HTTPレスポンス）← サーバ

URL    = 行き先
Method = やりたいこと（取得 / 送信）
Header = 条件や情報（ブラウザ情報など）
Body   = 送りたいデータ（主にPOST）
要素 意味 例
URL 行き先（どこに送るか） http://localhost:8080/app/list
Method やりたいこと（取得 / 送信） GET（取得）/ POST（送信・変更）
Header 条件や情報（ブラウザ情報など） Accept, Cookie, User-Agent …
Body 送りたいデータ（主にPOST） フォームの入力値など

チャプター2：HTTPリクエストを自分の目で見る（Chrome デベロッパーツール）

カバ先生：ブラウザが実際に送っている HTTP リクエストを、デベロッパーツールで目で見て確認します。「なんとなく知っている」から「実物を見た」に変わります。

前提：Google Chrome とは

Google Chrome は Google が開発したウェブブラウザです。Web 開発では事実上の標準ブラウザとして使われています。

  • 公式サイトからインストール：https://www.google.com/chrome/
  • インストール済みかどうかは、スタートメニュー（Windows）または Launchpad（Mac）で「Chrome」を検索して確認
  • この授業では Chrome を使うことを前提とします（Safari・Edge・Firefox ではメニュー名が異なります）

デベロッパーツールとは

カバ先生：デベロッパーツール（DevTools）は Chrome に内蔵された開発者向け検査ツールです。HTTP リクエスト・レスポンスの中身、HTML・CSS の構造、JavaScript のエラーなどをリアルタイムで確認できます。

開き方 操作
Windows F12 キー、または Ctrl + Shift + I
Mac Command + Option + I
右クリックから ページ上で右クリック →「検証」

HTTP リクエストを確認する手順（5ステップ）

  1. Chrome で任意のサイトを開く（例：学校のサイト、ニュースサイト）
  2. デベロッパーツールを開く（F12 または Ctrl+Shift+I）
  3. 上部タブから 「Network」 を選ぶ
  4. ページを更新（F5）すると通信の一覧が並ぶ
  5. 一覧の一番上にある document（HTMLファイル） をクリック → 右ペインの 「Headers」 タブを開く

カバ先生：Headers タブを開くと、次のような情報が確認できます。

  • General：Request URL（行き先）、Request Method（GET/POST）、Status Code（200=成功 / 404=見つからない 等）
  • Request Headers：ブラウザがサーバに送る情報（Host, User-Agent, Cookie など）
  • Response Headers：サーバがブラウザに返す情報（Content-Type, Set-Cookie など）

※ Network タブに何も表示されない場合は、DevTools を開いたまま F5 でページを再読み込みしてください。

チャプター3：クイズ（GET / POST の使い分け）

カバ先生：解答は折りたたみの中にあります。まず自分で考えてから開いてください。

【第1問】 GETメソッドについて、最も適切な説明はどれ？

  • A. リクエストボディ（Body）に主要データを載せて送るのが基本である
  • B. URLにパラメータが付くことが多く、同じURLなら再実行しやすい
  • C. 必ずデータ更新に使うメソッドである
解答例

正解：B

GETはURLに情報が乗りやすく、表示・検索などの「取得」によく使う。同じURLを再実行しても副作用が起きにくいのが特徴。

【第2問】 POSTメソッドがふさわしいケースはどれ？

  • A. 商品一覧を表示するだけの画面を開く
  • B. フォームの入力内容を送信して、登録処理を行う
  • C. 画像やCSSなどの静的ファイルを取得する
解答例

正解：B

POSTは送信するデータ（Body）を持ちやすく、登録・更新の処理で使う。URLに値が露出しないため、パスワードや個人情報の送信にも適している。

カバ先生：GET は「見るだけ（取得）」、POST は「送る・変える（送信）」と覚えておきましょう。Servlet の doGet / doPost に対応します。

チャプター4：Tomcatとディレクトリ構造（動画視聴 約10分）

視聴区間：35:43 〜 45:22（手動停止の目安：45:22）

各フォルダの役割（どこに何を置くか）

カバ先生：Tomcat はフォルダの場所でファイルの扱いを決めます。「公開する場所」と「非公開の場所」の2つがあります。

Tomcat/
 └ webapps/
    └ アプリ名（コンテキストルート）
       ├ HTML / CSS / 画像など  ← ブラウザから直接アクセス可能
       └ WEB-INF/              ← ブラウザから直接アクセス不可
          ├ classes/           ← コンパイル済みJavaクラス（.class）
          └ lib/               ← ライブラリ（.jar）
フォルダ 置くもの 外から直接見える？
webapps/アプリ名/ HTML, CSS, 画像 ✓ 見える
WEB-INF/classes/ コンパイル済み Java クラス ✗ 見えない
WEB-INF/lib/ ライブラリ（.jar） ✗ 見えない

カバ先生：WEB-INF の中に JSP を置く理由など、詳しい使い方は Servlet の「forward」を学んだ後で説明します。まずは「どこに何が入るか」の箱を覚えておいてください。

リクエストの流れ（まとめ） 

URL →（Tomcat）→ アプリに振り分け
リクエスト →（アプリ）→ 処理 → レスポンス

チェックポイント

Webの循環（矢印が必須）

  • ブラウザ →（HTTPリクエスト）→ Tomcat
  • ブラウザ ←（HTTPレスポンス）← Tomcat

Tomcatの箱の中

  • webapps → アプリ名 → WEB-INF → classes / lib

言葉で言えること

  • 「ブラウザはHTTPで依頼する」
  • 「Tomcatがアプリに渡して処理する」
  • 「処理結果がHTTPレスポンスで戻る」
